Conexão e autenticação

Configure uma credencial interna no servidor e comece pelas consultas de descoberta e saúde.

1. Configurar o servidor

Na raiz do projeto, execute o comando abaixo: ele gera e salva API_TOKEN em .env sem exibir a credencial. Se já existir um token no arquivo, o valor é preservado.

npm run api:token

Obtenha o valor de API_TOKEN no arquivo .env do servidor e configure-o no ambiente seguro da integração. Em produção, configure a credencial como segredo/variável de ambiente do serviço. O marcador abaixo é somente ilustrativo.

API_TOKEN="COLE_AQUI_O_TOKEN_GERADO_PELO_COMANDO"

O token precisa ter pelo menos 32 caracteres e não pode conter espaços, tabulações ou quebras de linha em nenhuma posição. Reinicie a aplicação após configurar ou trocar a variável. Em desenvolvimento, use npm run dev; em produção, reconstrua/inicie conforme o processo de implantação.

2. Enviar a credencial

Authorization: Bearer SEU_TOKEN
Content-Type: application/json

URL base local: http://localhost:3000/api/v1. Em outro ambiente, substitua o host e mantenha /api/v1. Todas as rotas exigem Bearer, incluindo health e OpenAPI.

A credencial é única e permite leitura e escrita de todos os recursos. Ela não representa um usuário ou uma sessão; os perfis admin/gestor do cadastro de usuários não limitam o token. Execute as integrações em um servidor ou ferramenta interna confiável. Não coloque API_TOKEN em JavaScript servido ao navegador, aplicativos públicos ou URLs; em ambientes remotos, use HTTPS.

3. Confirmar a instalação

export API_BASE="http://localhost:3000/api/v1"
export ALLE_API_TOKEN="SEU_TOKEN_GERADO"
curl --fail-with-body "$API_BASE/health" \
  -H "Authorization: Bearer $ALLE_API_TOKEN"

{
  "data": {"status":"ok","servico":"financeiro-alle","versao":"1.0.0","banco":"conectado"}
}

GET /api/v1 informa a versão e os recursos. GET /api/v1/openapi.json devolve a especificação completa, também incluída no arquivo api-v1.openapi.json entregue com este documento.

Formato, consultas e respostas

Use JSON nos corpos de POST e PUT. A API expõe o núcleo operacional; as importações CSV/XLSX continuam disponíveis pela interface do sistema.

AssuntoConvenção
Valores monetáriosStrings decimais com ponto, por exemplo "150.50". Até 10 dígitos inteiros e 2 casas; sem milhar. Evite números JSON para dinheiro. Entradas e saídas exigem valor positivo; comissão permite zero. Margem pode ser negativa.
IDs de cadastroInteiros positivos de 1 a 2147483647; o corpo aceita número inteiro seguro ou string. Agência, conta, UC e documentos devem ser texto para preservar zeros.
IDs financeirosBigint sempre como string. Máximo 9223372036854775807; inclui comissões, contas a pagar e id_do_registro de contas a receber. Não converta para Number no JavaScript.
DatasEntrada YYYY-MM-DD; saída ISO 8601 UTC, como 2026-10-16T00:00:00.000Z. Exiba datas civis preservando a parte YYYY-MM-DD para não deslocar o dia no fuso local.
CompetênciaYYYY-MM, por exemplo 2026-10; os serviços financeiros e de comissão também aceitam MM/AAAA.
POSTCria um registro; retorna 201 e {data: objeto}. IDs são gerados pelo servidor.
PUTSubstitui os campos editáveis. Envie todos os obrigatórios. Opcionais de texto/relação ausentes ou null são limpos. Flags de geração ausentes voltam a false e não aceitam null. Não é atualização parcial. PATCH não é aceito.
DELETEQuando disponível, exclui definitivamente e retorna 204 sem corpo. Vínculos podem impedir a exclusão. Não há DELETE para comissões.
ValidaçãoCampos desconhecidos, queries desconhecidas e parâmetros repetidos são rejeitados. Corpo máximo 64 KB. Use Content-Type: application/json.

Paginação e filtros

As coleções usam pagina=1 e limite=20 por padrão; limite máximo de 100. Filtros são combinados. As datas inicial e final são inclusivas. Consultar uma página além do total retorna data vazio; navegue pelo total de registros, sem assumir que uma página cheia implica outra página.

{
  "data": [
    {"id":1,"nome":"Distribuidora Exemplo"}
  ],
  "meta": {"pagina":1,"limite":20,"total":1,"paginas":1}
}

meta.total conta todos os resultados filtrados. Nas contas financeiras, meta.valor_total soma todos eles. Em comissões, meta.totais soma economia, empresa, parceiro e margem. Esses totais não se limitam à página atual. Cadastros são ordenados por nome/ID crescentes; contas a receber por data decrescente, datas nulas ao final; contas a pagar por vencimento/ID decrescentes.

Exemplo de filtros

http://localhost:3000/api/v1/comissoes?competencia=2026-10&status_recebimento=Pendente&pagina=1&limite=50

Codifique os valores da query com URLSearchParams ou equivalente; por exemplo, Não se aplica contém espaços e acento. Filtros são aceitos somente no GET da coleção; detalhe e escrita não aceitam query string.

Contas a receber

Recebimentos independentes e consulta das entradas financeiras geradas por comissões.

Contas a receber

GET /contas-a-receber · POST /contas-a-receber · GET /contas-a-receber/{id} · PUT /contas-a-receber/{id} · DELETE /contas-a-receber/{id}

Recebimentos. O ID da URL é id_do_registro, nunca id_do_pagamento. O servidor preenche beneficiario pelo titular da conta e metodo_do_pagamento pelo método selecionado. Consultas incluem tipo, parceiro, conta_bancaria, metodo e comissao:{id}|null. Movimentos ligados a comissão devem ser alterados pelo recurso comissoes.

O identificador usado em /{id} é id_do_registro. id_do_pagamento é apenas informativo. beneficiario, pagador, descricao e metodo_do_pagamento não são campos graváveis nesta rota. Recebido pode ter data nula conforme o serviço atual; sem data, fica fora dos indicadores por período.

tipo_idinteiro ou stringSimID do cadastro (inteiro de 1 a 2147483647).

Recebimento e pagamento independentes

A geradora paga a comissão à Alle; o parceiro recebe sua comissão. É possível pagar o parceiro antes de receber da geradora. Recebido exige data_recebimento; Pago exige data_pagamento. A comissão do parceiro é calculada pelo servidor em R$ 2,00, mesmo sem unidade ou parceiro vinculado. Sem beneficiário, o valor permanece Pendente e o pagamento exige o vínculo. Valores de comissões já pagas são preservados em edições. Na migração, comissões antigas ainda não pagas foram recalculadas para R$ 2,00, com ajuste da margem.

A combinação cliente/UC, geradora e competência deve ser única. A distribuidora precisa corresponder à cadastrada para o cliente; clientes sem distribuidora são associados à informada. Uma comissão antiga sem geradora bloqueia outra da mesma UC/competência até sua correção. Margem é calculada no servidor e não aceita edição direta.

Gerar movimentos financeiros

gerar_entrada=true exige status_recebimento=Recebido, data, conta_bancaria_id, metodo_id e valor_comissao_empresa positivo. gerar_saida=true exige parceiro, status_pagamento=Pago, data e valor_comissao_parceiro positivo. O servidor classifica os movimentos como Comissão e mantém a gravação vinculada à comissão na mesma transação.

Depois do vínculo, edite pelo recurso comissoes: os movimentos são sincronizados com valores, datas, competência e status. Uma entrada vinculada exige manter a comissão como Recebido. Uma saída vinculada exige manter parceiro e status Pago. Omitir flags em um PUT não remove vínculos existentes. As rotas financeiras recusam PUT/DELETE de movimentos vinculados com 409.

Vincular entradas ou saídas existentes

CampoCondições obrigatórias
entrada_existente_idA entrada deve estar Recebido e ter o mesmo valor da empresa, competência e data de recebimento. Se pagador estiver preenchido, deve identificar a geradora. Não pode estar ligada a outra comissão.
saida_existente_idA saída deve estar Pago e ter o mesmo parceiro/favorecido, valor do parceiro, competência e data de pagamento. Não pode estar ligada a outra comissão.

Informe o ID existente como string. Não combine vincular e gerar no mesmo lado; também não substitua um vínculo já existente por outro. Os campos entrada_id e saida_id aparecem apenas nas respostas.

Operações em lote

Ambas exigem de 1 a 100 IDs de comissão, enviados como strings, sem repetições. Todo o lote é processado na mesma transação; um ID inexistente ou uma regra impeditiva cancela as alterações. Marcar status em lote sincroniza movimentos já vinculados e não cria novos lançamentos.

// Execute em Node.js (fetch nativo), no servidor da integração.
const base = process.env.ALLE_API_BASE ?? "http://localhost:3000/api/v1";
const token = process.env.ALLE_API_TOKEN;
if (!token) throw new Error("Configure ALLE_API_TOKEN");

async function api(path, method = "GET", body) {
  const response = await fetch(base + path, {
    method,
    headers: {
      Authorization: "Bearer " + token,
      ...(body === undefined ? {} : { "Content-Type": "application/json" })
    },
    ...(body === undefined ? {} : { body: JSON.stringify(body) })
  });
  if (response.status === 204) return null;
  const result = await response.json();
  if (!response.ok) {
    throw new Error(response.status + " " + result.error.code + ": " +
      result.error.message);
  }

Erros, retornos e integração

Leia o status HTTP e o objeto error. Não trate uma resposta 204 como JSON.

HTTPSignificadoComo agir
400Requisição inválidaCorrija JSON, ID, paginação, campo desconhecido, query desconhecida ou repetida.
401Token ausente ou inválidoConfira Authorization: Bearer e o token configurado; a resposta informa WWW-Authenticate: Bearer.
404Não encontradoConfira a rota e os IDs do registro e dos cadastros relacionados.
405Método não permitidoUse os métodos do catálogo. O cabeçalho Allow informa os aceitos; comissões não oferecem DELETE.
409ConflitoPode ser chave única, vínculo protegido, movimento ligado a comissão ou atualização concorrente. Consulte o estado atual antes de repetir uma gravação.
413Corpo muito grandeReduza o objeto JSON para no máximo 64 KB; lotes de comissões também têm limite de 100 IDs.
415Tipo de conteúdo inválidoEnvie Content-Type: application/json em POST e PUT.
422ValidaçãoCorrija campos obrigatórios, dinheiro, datas, status, flags e regras de negócio descritas na mensagem.
500Erro internoRegistre horário, rota e status para suporte; o servidor não expõe detalhes sensíveis na resposta.
503IndisponívelConfirme API_TOKEN no servidor, reinicialização e conexão ao banco.

{"error":{"code":"validation_error","message":"Informe uma data válida."}}

Os códigos de erro são strings; exemplos: unauthorized, not_found, method_not_allowed, unknown_field, validation_error, invalid_field, duplicate_record, related_record, commission_linked, concurrent_update, api_not_configured, database_unavailable e internal_error. A mensagem pode variar conforme o campo ou a regra que falhou.

Gravações e exclusões

Não há chave de idempotência. Em falha de rede depois de POST, consulte a chave natural/registro antes de reenviar para evitar duplicidade. Para comissões, a unicidade cliente/geradora/competência ajuda a identificar um registro já criado. Exclusões protegidas não são em cascata; consulte e resolva os vínculos antes de repetir.
